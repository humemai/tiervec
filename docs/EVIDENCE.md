# Evidence

This page lists the studies behind what the repository says about tiervec: the question, what the result does and does not claim, the commit it ran on, the command, and the result files. The files hold numbers only, and the tables here are printed from them by [`scripts/evidence_tables.py`](../scripts/evidence_tables.py):

```
uv run scripts/evidence_tables.py --check
```

A study is listed when its files are in the repository.

| Study | Data | Result files |
|---|---|---|
| [#106](https://github.com/humemai/tiervec/issues/106), generated data | clustered Gaussian, 768 dimensions, 100,000 and 1,000,000 vectors | [`results/106/synthetic/`](../results/106/synthetic) |
| [#106](https://github.com/humemai/tiervec/issues/106), real embeddings | DBpedia entities, OpenAI embeddings cut to 768 dimensions, 100,000 and 999,000 vectors | [`results/106/real/`](../results/106/real) |

## #106, generated data

| Field | Content |
|---|---|
| Question | Does recall at the default `ef` hold from 100,000 to 1,000,000 vectors, and if not, is it the merge or the build parameters? |
| Claims | recall@10 of the tier against an exact scan on one generated distribution, one run per arm. On this data the default build loses recall at 1,000,000 vectors, a larger `M` and `efConstruction` win much of it back, and one rebuilt segment in place of adds and merges does not. |
| Does not claim | Any speed: each arm ran once, on four low-power cores of a laptop that may have run other work, so the latency columns show a direction only. Nothing about real embeddings: the [run on real embeddings](#106-real-embeddings) did not show this drop. Nothing about other dimensions, filters that follow the vectors, other hardware, or a write rate the tier can sustain (the writers were throttled). |
| Data | Generated by the harness from seed 42: 100 clusters, sigma 0.4, cosine ([the data](BENCHMARKS.md#the-data)). |
| Pin | Commit [`70d5dee`](https://github.com/humemai/tiervec/commit/70d5dee6c373c7cd547ef3c3c9d685e849c3f820), JDK 25. Each file names the processor, its flags, the memory, the JVM arguments, and every option. |
| Command | Check out the commit, compile the harness as in [Run it](BENCHMARKS.md#run-it), then run one of the commands [below](#commands). |
| Order | The first two runs came first. The three runs of the follow-up (d1 to d3) were defined after the drop was seen, and before they ran. |
| Reading the files | The three files of the follow-up have two unfiltered cells at `ef` 100, one from the main run and one from the later sweep. Their recall agrees, and the tables show the cell of the sweep, as the tables in #106 did. |
| Edits to the files | In the `PARAMS` line of each file, the two local paths (`out` and `repo`) are replaced. Nothing else is changed. |

## #106, real embeddings

| Field | Content |
|---|---|
| Question | Does recall at the default `ef` hold from 100,000 to 1,000,000 real vectors, and what do a larger `M` and `efConstruction` change? |
| Claims | recall@10 of the tier against exact answers on one real set, one build per arm. On this set the default build loses little recall from 100,000 to 999,000 vectors: the difference at `ef` 100 is under the bar that was written before the runs ([the differences](#differences-at-ef-100)), so the drop seen on the generated data did not appear here. The larger build had higher recall at 1M at `ef` 100 and took longer to settle. |
| Does not claim | Any speed: each arm was built once, on six efficiency cores with turbo off, in a run that was not a timed study and may have shared the machine with other work, so the latency columns show a direction only. Nothing about other real sets, the native 1,536 dimensions, other hardware, filters that follow the vectors, writes that run beside searches (these runs have no concurrent phase), or the right defaults for other data. Recall is a mean over the queries: single queries do much worse ([the lowest](#lowest-recall10-of-a-single-query-by-ef)). A build is not bit-for-bit repeatable, because seals run on background threads, and no arm was built twice. |
| Data | The DBpedia entities set with OpenAI `text-embedding-3-large` embeddings (1,536 dimensions, 1,000,000 rows). Every vector is cut to its first 768 coordinates and then scaled to length 1. 1,000 rows are held out as queries (seed 42), which leaves an index of 999,000 vectors, called 1M here. The 100,000-vector index (100k) is a uniform random subset of those rows (seed 42) with the same queries and its own exact answers. The vectors and the texts are not in the repository: the texts carry a share-alike licence. |
| Pin | Commit [`70b64f2`](https://github.com/humemai/tiervec/commit/70b64f2e342430cb0c6389a187c35328219aca2e), JDK 25. Its `src/main` is the same as at the commit of the generated-data runs. Each file names the processor, its flags, the memory, the JVM arguments, every option, and the data checksum. |
| Preparing the data | `scripts/prep_real_dataset.py` of the pinned commit converts the set at its full dimension ([Real data](BENCHMARKS.md#real-data)). The cut to 768 coordinates and the subset were made by a study script that imports it, [`prep_set.py`](https://github.com/humemai/tiervec/blob/main/research/106-real-embeddings/prep_set.py); its usage is at the top of the file. The `DATASET` line of each file records both rules and the checksum of the imported script. I published the script as a record and have not run it from the repository, so I do not claim that it rebuilds these data files from a fresh checkout. |
| Command | Check out the commit, compile the harness as in [Run it](BENCHMARKS.md#run-it), put the prepared data under `data/`, then run one of the commands [below](#commands-on-real-data). The runs were pinned to cores 12 to 17 from outside the command. |
| Order | The three arms and the bar were written down before the first run, and the arms ran in the order of their names. |
| Reading the files | Each file has two unfiltered cells at `ef` 100, one from the main run and one from the later sweep. In the two 1M files their recall agrees. In the 100k file it does not ([both cells](#the-two-cells-at-ef-100)). The tables show the cell of the sweep, as the tables in #106 did, and the difference from 100k to 1M is under the bar with either cell. The 100k build ended with vectors still in the exact tail and the 1M builds did not; the file does not record whether the tail changed between its two cells. |
| Edits to the files | In each file the host label (in the `RUN` and `PARAMS` lines) and the local paths (`data`, `out`, and `repo` in the `PARAMS` line, `path` in the `DATASET` line) are replaced. Nothing else is changed. |
