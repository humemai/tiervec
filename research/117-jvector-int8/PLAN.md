# jvector native INT8 against FP32 on the release 4.1.0-rc.1 (#117), written on 2026-11-24 before any timed run

This is an edited copy of the plan I wrote before the timed runs. I removed local paths, the host name, references to private notes, and the section on the plumbing checks. The question, the arms, the rules, and the thresholds are the originals. The results I posted are in [this comment on #117](https://github.com/humemai/tiervec/issues/117#issuecomment-7142383382).

Run ids (the `OUT` label of a run): `i8rc1n-sift128_d1536_d768_d256` (jar as shipped, native provider) and `i8rc1p-sift128_d1536_d768_d256` (Panama forced, like-for-like with the earlier run): two jobs of four cells each, run in that order. Each cell has its own folder, its own A/A, and its own analysis, and a cell that ends INVALID or WEAK does not stop the next one. One confirmatory rerun of a GRAY cell, if declared below, takes the label of that cell alone with the suffix `-r2` (for example `i8rc1n-sift128-r2`). `i8rc1?-smoke*` labels are plumbing only and report nothing.

## What this repeats and what differs

The earlier measurement (https://github.com/datastax/jvector/pull/709#issuecomment-6558622218, and the follow-up with 256-d) compared `jv-INT8` with `jv-FP32` on the head `575dcee1b` of jvector PR #709, built as pushed, on a laptop. Facts checked 2026-11-24: PR #709 merged 2026-11-23 06:10:29Z, merge commit `ee81b2e7d6dfa2a263e281c9929c8263b71f21eb`; release 4.1.0-rc.1 published 2026-11-23 17:54:19Z, an annotated tag whose commit is 3 commits after the merge commit (`gh api compare`: ahead_by 3, behind_by 0, so the merge commit is an ancestor of the tag); the release is on Maven Central as `io.github.jbellis:jvector:4.1.0-rc.1`, jar sha256 `16d609b5eec7864bf5d984c0e03d0e3ba1ec0d77c159b46d9bb4400e0b898528` (the sha256 that Central publishes; `jars/CENTRAL.sha256`). Its multi-release jar carries `META-INF/versions/20` (Panama) classes and, new since the earlier run, `META-INF/versions/22` (native) classes and the shared libraries `libjvector-x86_64.so`, `libjvector-aarch64.so`, `libjvector_ash_fp16-*.so` inside the jar. The earlier run used the Panama provider because the build of the PR head had no native library. With the release jar and no setting, jvector 4.1.0-rc.1 selects `NativeVectorizationProvider` (seen in the dry run; the property is `jvector.vectorization_provider`, values `panama` and `native`). So there are TWO sets of runs, both declared before any run: `n` = the jar as shipped, default provider (native, the library's Highway kernels, which this study did not build and does not alter), and `p` = the same jar with `-Djvector.vectorization_provider=panama` in every JVM, the provider of the earlier run and therefore the like-for-like repeat. `run_ab.sh` records the provider of every arm run (`"vectorization"` in the harness's INFO line) and makes a cell INVALID if any run reports another provider than the label says (a native library that fails to load falls back to Panama silently).

Same as the earlier run: the harness (`src/main/java/vq`, only version labels changed), the cells (`sift128-100000`, `dbpedia-openai3-1536-100000`, `-768-`, `-256-`: 100,000 base vectors, 1000 queries, recall@10 against exact ground truth, the same `.npy` arrays, sha256 in `data.sha256`), the graph parameters (M 32, beam 100, overflow 1.2, alpha 1.2, no hierarchy), the byte conversions of `Int8Example` (uint8 shift for SIFT, one global scale 127 / max|x| for DBpedia), INT8 scoring end to end without a native kernel, the matched-recall rule (each arm timed at the cheapest tested `(efSearch, rerank)` of the grid {0, 20, 50, 100, 200, 400} x {0, 5, 10} whose recall@10 is at least 0.95, calibrated on THIS build), JDK (GraalVM Community 25.0.4.1.1), JMH (`-f 1 -wi 3 -w 2s -i 5 -r 2s`, fresh JVM per run, 4g heap), the metrics (p50, p95, p99 of the sample mode, throughput with 1 and 2 threads), the arm order (ABBA, rotated by 5 per round), the interval method (median of per-round ratios, bootstrap 95% interval), and the engine jars of the wheel 26.10.2.post1 on the classpath (`wheel-jars.sha256`).

Differs, and nothing else: (1) the jvector jar: the 4.1.0-rc.1 release jar from Maven Central, not the build of PR #709 head `575dcee1b` (the release is 3 commits after the merge commit, and the merge differs from the head, see below); (2) the host and lane: a benchmark host (i9-12900HK, 20 threads, 61 GB), cores 0 and 2, started and pinned by my job runner, not the laptop (Core Ultra X9 388H, cores 6 and 7); the benchmark host runs with turbo off and the governor `powersave`, so absolute microseconds are not comparable with the laptop and only the ratios are; (3) a third arm Z = `jv-FP32-aa` (FP32 again, same prepared graph and setting, interleaved in every round) as the A/A control, which the earlier run did not have; (4) the harness's own bookkeeping that depended on the laptop: no night lock and no taskset (the job runner sets the CPU affinity), no noise log (so the COLLISION rule of the interval script cannot fire; foreign load is watched by the job runner, which halts the job), and the thermal wait and the 2 C cooling are `arm_gate` in `run_ab.sh`; (5) untimed prep runs first inside the same job, on the same two cores (the earlier run prepped on six cores before); (6) the code: the PR head of the earlier run was revised several times before the merge (per its thread: rebase, review changes, the graph index format v7, the zero-vector check under cosine, the score normalisation of the byte similarities, release notes), and the release is 3 commits after the merge; a difference between the earlier numbers and the new ones is not claimed to be caused by any one change; (7) the vectorization provider, see above.

The numbers of the earlier run stay as posted. They are information next to the new ones: no pooling, no figure of the rule below reads them.

## The ten points

1. **Arms.** A = `jv-FP32`, B = `jv-INT8`, Z = `jv-FP32-aa` (A again). All three run on the same jar (sha256 above; the arm lines of each cell's analysis name the jar, and the JMH log of every run names it in `jvector_jar=`).
2. **Figures by role.** Gating: lat50 (p50) of B against A in each of the four cells. A/A (validity): lat50 of Z against A in each cell. Information, reported and never deciding: lat95, lat99, qps at 1 and 2 threads, recall@10 and recall@1 over the grid, the calibrated settings, build time, index bytes, peak RSS, every A/A figure. The 256-d and 768-d cells are reported like the other two (as in the earlier follow-up, 1536-d and 128-d were the main cells).
3. **Verdict rule per cell (p50, `aa_check.py`).** INT8-FASTER if the upper end of the 95% interval of the median B/A ratio is at most 1.00, INT8-SLOWER if its lower end is above 1.00, GRAY otherwise. Nothing is adopted by this study (#117 says the adoption is decided by these numbers together with #72 and not before #106 is read), so there is no recommendation rule; the words INT8-FASTER, INT8-SLOWER, and GRAY are descriptions of the interval. "No difference" is written only if the whole interval lies inside [0.97, 1.03]; otherwise "not resolved (CI [lo, hi])".
4. **Validity before verdict.** INVALID (exit 2, report nothing, new OUT): the median of the Z against A lat50 outside [0.97, 1.03] with at least 10 clean pairs, a COLLISION in either lat50 figure, a figure block missing, a jar or data sum that differs (exit 6). WEAK (exit 3, report nothing, new OUT): fewer than 10 clean pairs on either lat50 figure at the cap. An arm run that fails stops the job (exit 4) and the files stay on disk.
5. **Stopping rule.** Rounds 0..12 (round 0 is dropped as warm-up), then one more round at a time until every figure of every pair has at least 10 clean pairs, hard cap round 20. No round is added because a result looks close.
6. **Confirmatory rerun: ONE, declared in advance.** A cell whose outcome is GRAY gets exactly one rerun with the identical arms, jar, pins, and rule, `OUT=<label>-r2`; it is final and both runs are reported. INT8-FASTER and INT8-SLOWER are final. A rerun after INVALID or WEAK replaces a run that reported nothing and is not the confirmatory one.
7. **Non-speed adoption.** Not applicable: nothing is adopted. Memory and file-size figures (index bytes, peak RSS) are reported as information, with the harness's caveat that it keeps the fp32 base on the heap in both arms.
8. **Changes after a run.** Any change of arms, cells, settings, thresholds, or pins after a timed run is a new study with a new section written before it. `SHA256SUMS` (scripts, sources, classes, jar, data, and wheel jars) is checked by `run_ab.sh` before every run; `report.py` is the one reporting file outside it (a bug there may be fixed after the run, and every number it prints is checked against the interval output).
9. **Reporting.** Every number in a post is generated by `report.py` from the result files and checked by script before posting. Intervals, never a single percentage. Named: jvector 4.1.0-rc.1 (merge commit `ee81b2e7d6` is an ancestor of the tag), the jar sha256, the host, the cores, the JDK, the engine jars of the wheel. INVALID and WEAK runs stay on disk with their reason and are not reported.
10. **Precedent.** The earlier run (no A/A, laptop) and another study of mine with an interleaved A/A and a rerun clause declared up front.

## Estimate

The lock-held time of the earlier run per cell was 0.38 h (sift128, 13 rounds), 0.47 h (1536-d, 15), 0.61 h (768-d, 20), and 0.41 h (256-d, 14); with the third arm about 1.5 times that, about 2.8 h per set and about 5.6 h for both sets, plus prep on two cores. A model, not a measurement of the benchmark host.
